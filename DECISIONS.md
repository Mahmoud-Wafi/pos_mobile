# DECISIONS.md

Architectural and business-rule decisions made during development.

## Phase 1

### D-001 — Safety copy path for restore
**Decision**: The `restore_backup()` function saves a safety copy of the current DB in the same directory as `DB_PATH` (not in `BACKUP_DIR`), named `shop_safety_<timestamp>.db`.  
**Reason**: Safest option — keeps the last known good copy separate from the backup archive, preventing circular overwrites.

### D-002 — Alembic for production; `init_db()` for tests
**Decision**: Production uses `alembic upgrade head`; tests call `init_db(engine)` directly with an in-memory SQLite engine.  
**Reason**: Keeps tests fast, isolated, and independent of the migrations history, while production always goes through the migration path.

### D-003 — `python3.10` as the interpreter
**Decision**: All commands use `python3.10` because the packages (SQLAlchemy, Alembic, pytest) were installed with `pip3 install --user` which targets the `python3.10` user site-packages (`~/.local/lib/python3.10/`).  
**Impact**: `requirements.txt` pins compatible versions; `python3` symlink on this Ubuntu system points to 3.10 as well for the user path.

### D-004 — Default manager credentials
**Decision**: Seeded manager account: username=`admin`, password=`admin123`.  
**Reason**: Development convenience only. Production deployments must change this on first login (enforced by a future Settings screen prompt).

### D-005 — `PermissionDenied` raised in services, not silently swallowed
**Decision**: Any service call that violates RBAC raises `PermissionDenied` immediately, even if the UI has hidden the button.  
**Reason**: AGENTS.md §2 rule 5 explicitly requires this.

## Phase 2 — Inventory

### D-006 — Dual IMEI uniqueness checking
**Decision**: Uniqueness is strictly enforced across both `imei1` and `imei2`. An IMEI cannot exist as `imei1` or `imei2` on any device in the database.
**Reason**: Prevents duplicate registration of dual-SIM devices or cross-referencing conflicts.

### D-007 — Stock integrity for IMEI items vs Non-IMEI items
**Decision**: For non-IMEI items, `stock.quantity` is driven by and equals the sum of `stock_movements.quantity`. For IMEI items, `stock.quantity` mirrors the live count of devices with `status='in_stock'`.
**Reason**: Aligns with AGENTS.md §5: "for non-IMEI items; for IMEI items quantity = count of devices in_stock".

### D-008 — Excel Import Format
**Decision**: The importer accepts both Arabic and English header names (e.g. `الاسم`/`name`, `الباركود`/`barcode`, `الكمية`/`quantity`) and converts Egyptian Pound amounts to integer piasters using `egp_to_piasters`.
**Reason**: Maximum user convenience when importing vendor price lists or existing shop sheets.


## Phase 0/1 — Foundations & security

### D-009 — Time: store naive UTC, think in Africa/Cairo
**Decision**: The DB keeps naive UTC datetimes. `app/core/clock.py` is the only place that converts; days, daily close, reports, wallet quotas, invoice numbers and printed times use the shop's local day (`day_bounds_utc`, `local_today`, `fmt_local`). Override the zone with `POS_TIMEZONE`.
**Reason**: sales between 00:00 and 02:00/03:00 Cairo time were previously counted in the previous day.

### D-010 — Data in a per-user folder; Alembic runs at start-up
**Decision**: `DATA_DIR` defaults to `%APPDATA%/MobileShopPOS` (Windows) / `~/.local/share/MobileShopPOS`; `POS_DATA_DIR` overrides. `startup.run_migrations()` upgrades to head (legacy `create_all` databases are stamped). Logs go to `DATA_DIR/logs/app.log`.
**Reason**: the packaged app cannot write beside its own files and users must not run Alembic by hand.

### D-011 — Login, idle lock and first-login password change
**Decision**: `SessionController` owns login -> main window -> logout/lock. Idle timeout comes from the `idle_lock_minutes` setting (0 disables). Accounts still using a seeded default password must change it before continuing (detected by verifying the known defaults, no schema change).

### D-012 — UI permission map is a hint, services still enforce
**Decision**: `app/ui/access.py` decides which screens are shown per permission set; views a user cannot open are not even constructed.

## D-013 — Cart editing, held invoices, invoice history
- `sales_service.update_line` edits qty/price/line discount on an unposted sale; a price different from the catalogue or a discount above the cashier limit needs a manager (`manager_override`).
- Empty drafts are never listed as held and are discarded when a new invoice starts; clearing the cart deletes the draft.
- `remove_line` now expires `sale.items` (totals were summed over the deleted row before).
- Invoice history is a separate screen (`invoices`); cashiers only see their own invoices (enforced in `search_sales`), void is manager-only.
- Devices are offered oldest first (FIFO).

## D-014 — Design system
- Tokens in `app/ui/design/tokens.py`; the global QSS is generated by `qss.py`. Widgets style through dynamic properties (`variant`, `card`, `banner`, `tone`, `size`, `bold`, `nav`/`active`) set with `app/ui/design/style.py`, not inline styles. Limit: 15 inline `setStyleSheet` calls (a test enforces it); the rest are dynamic brand colours.
- Icons: Lucide (ISC licence, not MIT as the brief said) bundled in `assets/icons`; `auto_icons.py` adds an icon to text buttons from Arabic keywords. Emoji are no longer used as icons.
- Errors: `show_error` shows Arabic business messages only; any other exception is logged and replaced by a generic Arabic text. Success messages are toasts; destructive actions use `ConfirmDialog`.
- Window geometry is stored in `DATA_DIR/window.ini`.

## D-015 — Backups, import/export, dashboard, tables, sessions
- Backup = zip of `shop.db` (SQLite online backup API) + `manifest.json` (format, app version, Alembic revision, UTC time, sha256). Restore verifies everything first, keeps a safety copy (plain `.damaged.db` copy if the live DB is corrupt), disposes the engine, removes `-wal`/`-shm`, replaces atomically and offers a restart. Retention default 14; auto-backup daily and on close (if the last one is over an hour old).
- Import: Arabic/English headers (D-008), preview with per-row errors, then commit. Export: real RTL `.xlsx` or CSV with BOM; cost columns only with `cost.view`.
- Dashboard data comes from `report_service.dashboard_overview`, which hides sections the user lacks permission for; charts use QtCharts (offline).
- Tables: an app-wide event filter (`table_defaults.py`) applies row height ≥ 40, alternating rows and remembered column widths (`DATA_DIR/ui.ini`); `DataTable` adds numeric-aware sorting and keys that survive sorting. Existing screens that read rows by index must move to `selected_key()` before opting in to sorting.
- Sessions: the shared session is rolled back and expired on every screen switch. A full session-per-action refactor was deliberately not done in this phase (risk vs. benefit; services still take a session argument so it can be done screen by screen later).

## D-016 — Repairs, warranty claims, labels, off-site backup
- Repairs use the existing `sales.create` permission (cashier and manager); cancelling uses `sales.return`; entering parts cost needs `cost.view`. No new permission was added so existing databases need no role migration.
- Cash taken for a repair goes into the drawer under the user's open shift (category `repair`), so shift close and the daily close see it. Repair profit (final price - parts cost) is counted in the daily close on the day the device is delivered, not on intake.
- A repair can only be delivered when it is `ready` and fully paid. Cancelling an open ticket refunds what was paid out of the drawer.
- Warranty claims on an expired warranty are allowed but recorded with `in_warranty = false` (the owner decides goodwill cases).
- Labels are PDFs (no printer driver code): the shop prints them to its label printer. IMEI labels carry no price.
- Off-site copy: written under a temp name, verified, then renamed; failures never stop the local backup and show in the status bar.
- The "ready" message opens `https://wa.me/...` in the user's browser; the app itself stays offline.

## D-017 — Editing and deleting stock
- The first versions only had create (and a service-level `update_product` with no screen). Products and devices can now be edited from their lists (button or double-click).
- The stock ledger and the books must stay consistent, so "delete" is guarded: a product can be deleted only if it never had sales, purchases, devices or stock movements — otherwise it can be deactivated (hidden from POS). A device can be deleted only if it was added by mistake (in stock, no purchase/sale/used-intake link); its own ledger row goes with it. Any other in-stock device is taken out with «إخراج من المخزون» (status `damaged`, a -1 `adjust` movement and a required reason).
- Type and IMEI tracking are locked once a product has history. A device's IMEI, condition and costs can only be edited while it is in stock; sold devices accept notes only.
- Cost fields (product cost, device purchase/extra cost, the device list's cost column) need `cost.view`; a cashier no longer sees them.
- Not covered yet: renaming/deleting categories and brands.

## D-018 — Several barcodes per product
- A product keeps its main `barcode` and any number of extra codes in `product_barcodes` (unique across both). Lookups (`find_product_by_barcode`) accept the main code, an extra code, or the internal label code `P` + 6-digit id, after normalising Arabic-Indic digits, spaces and scanner line breaks.
- A barcode can belong to one product only; entering a code that exists opens that product instead of creating a duplicate.

## D-019 — Locale-independent number input; wallet management is manager-only
- Qt's `QDoubleValidator`/`QIntValidator` follow the OS locale. On an Arabic (Egypt) Windows they reject `500.00`, so users could not type decimals in any money field. All 48 uses are replaced by `app/ui/components/numeric.py` (`set_money_validator`, `set_int_validator`), which accept ASCII and Arabic-Indic digits and `.`, `,` or `٫` as the decimal mark on every machine.
- `app.core.money.normalize_number_text` is the single normaliser: a comma is a thousands mark only when it groups three digits (`1,234`), otherwise it is a decimal mark (`500,5`). `parse_egp_input`, `egp_to_piasters(str)`, `parse_percent_to_bp` and `parse_int_input` all use it.
- Creating wallets and commission rules needs `wallet.manage` (manager). The wallet screen now hides those buttons for roles without it; the service still enforces the rule. Change the role grants if the wallet employee should manage wallets too.
- A purchase invoice can create a product in place ("+ منتج جديد"). The opening-quantity field is hidden there because the invoice itself adds the stock.
- `tests/test_ui_service_calls.py` statically checks that every `*_service.fn(...)` call in the UI matches the real signature.

## D-020 — Supplier ledger, editable commissions, model picker, hardware settings
- **Supplier ledger.** Every payment to a supplier is a `SupplierPayment`; a payment made while entering an invoice is also one (`CashTransaction.category = "purchase"`). Payments may be linked to an invoice (`purchase_id`) and then update that invoice's `paid` / `balance`. Clicking a supplier opens a ledger dialog: invoices, each invoice's payments in date order, and totals (e.g. 10000 invoice paid 5000, 2000, 1000, 2000 shows every step and the remaining balance). `pay_supplier` no longer checks drawer sufficiency, to stay consistent with `create_purchase`.
- **Commission rules are editable** (`update_commission_rule`, `delete_commission_rule`, manager only). `max_amount == 0` means unlimited; delete is soft (`is_active = False`); overlapping ranges on the same network and operation are rejected.
- **ModelPicker.** The phone-model field in "add device" and "used device" was a read-only combo, so typing did nothing. It is now an editable combo; typing a new model name creates a phone product (`track_imei`, sale price from the price field) when saved.
- **Repair delivery** is one step: «تسليم» can mark the ticket ready and deliver it (`deliver(..., mark_ready=True)`) once it is fully paid, instead of failing on a ticket that was not yet "ready".
- **Hardware settings tab** separates the receipt printer (name, direct print, width mm), the label printer (name, direct print, label width/height mm) and a barcode-reader test field. Labels print through reportlab PDFs rendered with QtPdf onto the chosen printer, or open as a PDF when direct printing is off.
- UI polish: reports/profit, backup screen, customer/debt action buttons (QSS rule for buttons inside table cells), cash-ledger category names in Arabic.
- Not covered: category/brand edit and delete; Windows `.exe` build is untested.

## D-021 — One licence per computer
- The app refuses to start past the activation screen on a computer without a valid licence, so a copied exe/folder does not run elsewhere. Fully offline.
- Machine code = SHA-256 of the OS install id (Windows `MachineGuid`, Linux `/etc/machine-id`, macOS `IOPlatformUUID`), shown as `XXXXX-XXXXX-XXXXX-XXXXX`. Activation code = Ed25519 signature of that code. The public key is in `app/core/license.py`; the private key stays with the owner (`license_private.key`, never committed or shipped). `tools/make_license.py` creates codes.
- The licence is permanent. A new computer, or a changed OS install id, needs a new code from the owner (manual re-activation, by choice).
- The activation code is stored in `license.key` in the data folder; copying that file to another computer does not work because the signature covers the machine code. `reset_data.py` does not delete it.
- Limit: this stops casual copying, not a determined developer who patches the code; ship only the built exe, never the source.

## D-022 — Audit fixes: stock, change, returns, profit, shifts, supplier payments
- **Stock:** quantities are totalled per product before posting (`post_sale`, `update_line`); the same IMEI cannot be on two lines. Posting first takes SQLite's write lock and re-reads stock, so two cashiers cannot spend the same units (the second fails). Only a manager (or a manager's approval) may sell below zero stock; it stays allowed and audited.
- **Change:** only CASH can be over-tendered. The drawer receives the net cash; `sales.cash_tendered` / `sales.change_given` keep the receipt facts (migration d5f1b3c7a901, existing rows default to 0). Wallet/bank/credit amounts above the invoice total are rejected. Payment rows are stored net, so they always add up to the invoice.
- **Returns:** zero/negative quantities and empty requests are rejected; everything is validated before anything is changed; the same line twice in a request is summed; refunds are proportional and sum exactly to the line total. A refund first cancels what the customer still owes on THAT sale (not unrelated debt), the rest goes back as cash out of the drawer, attributed to the user's open shift or else the shop's open shift. Void returns only what was not returned yet.
- **Profit (`app/services/sales_profit.py`):** a sale's profit stays in the period of the invoice (posted and voided invoices); a return reduces revenue in the period of the return, and reduces cost only if restocked (a non-restocked return keeps its cost as a loss). Profit report, sales report, dashboard and daily close all use this one definition.
- **Shifts:** expected cash counts DRAWER movements only (a bank-paid expense does not), including transfers in/out of the drawer. Supplier payments and purchase down-payments from the drawer now carry the shift. At close, the drawer's book balance is adjusted to the counted cash with a `shift_diff` entry (not counted in "expected"); the shortage/overage reaches the P&L once, through `Shift.diff`.
- **Supplier payments:** refused when the account balance is not enough (same as expenses and transfers), also for the down-payment of a purchase invoice; a general payment cannot exceed what is owed; an invoice payment cannot exceed the invoice balance. This replaces the earlier choice in D-020 to skip the funds check.
- **Permissions:** `add_line`, `remove_line`, `update_line` now require `sales.create` inside the service.
- **IMEI:** the services require 14-16 digits and reject IMEI1 = IMEI2 and duplicates inside one batch (Luhn stays advisory in the UI because some genuine devices fail it).
- **Not changed / owner to confirm:** vodafone/instapay sale payments are recorded as payment methods only; they do not change a wallet's balance (the payment dialog has no wallet picker). A returned device that is not restocked keeps status `sold`.

## D-023 — Audit round 2
- **Used-device purchase** now follows the same rules as every other payment out of an account: the balance must cover the price, and a drawer payment is attributed to the open shift (so the shift no longer shows a false shortage).
- **One IMEI rule** (`app.core.imei.clean_imei_pair`): Arabic digits normalised, digits only, 14-16 long, IMEI 1 required and different from IMEI 2. Used by adding a device, editing a device, purchase invoices and used purchases. Luhn remains advisory in the UI.
- **Payment methods** are a closed list (`cash, vodafone, orange, etisalat, instapay, card, bank, credit`); anything else is refused. **Refund methods** are the same list without `credit`.
- **Refunds go back the way the money came:** the drawer returns at most the CASH actually received on that sale (minus cash already returned); the rest is a non-cash refund that is recorded on the return but makes no drawer entry. Fixes a void of a wallet-paid invoice paying cash out of the drawer.
- **`sales.remaining`** is now what the customer still owes on the invoice after returns (unpaid at posting minus the returned value, never below zero); `paid` and `total` stay as posted.
- **Windows build:** a real PyInstaller build and start-up test exposed a crash in the frozen app (`logging.config` was not bundled, needed by Alembic's env.py). Fixed in the spec; the build script now creates a clean venv, builds, checks the exe exists and makes a ZIP. A Windows run on a clean PC is still required.

## D-024 — Dialogs always fit the screen
- **Problem:** tall dialogs (e.g. add product, ~900 px) were taller than small laptop screens, so the save/cancel buttons were off-screen.
- **Rule:** one application-wide event filter (`app/ui/design/dialog_fit.py`, installed in `setup_theme`) runs on the first show of every dialog. If the dialog needs more than 92% of the available screen height, its content is moved into a scroll area and the trailing button row is pinned under it, so the buttons never scroll away. Width is kept large enough for the content (horizontal scroll only if the screen is narrower). Every dialog is also clamped to the screen and moved on-screen.
- Dialogs that already fit are left untouched. No per-dialog code is needed; new dialogs get this automatically.

## D-025 — Visual redesign (tokens first)
- The whole look comes from `app/ui/design/tokens.py` + `qss.py`; screens were not rewritten. New palette (ink navy shell `#0E1630`, primary `#3558F0`, cool greys), 16 px card radius (`RADII["xl"]`), 44 px controls, pill badges, segmented tabs.
- The header and sidebar are one dark shell; the active page is a solid primary button. Below 1280 px window width the sidebar becomes an icon-only rail (tooltips keep the names) so pages keep their width on 1366/1024 screens.
- Old hard-coded slate/tailwind colours in the table widgets were mapped to the new tokens. Wallet brand colours are unchanged on purpose.
- Inventory (products and devices) toolbars: the main actions (search, filter, add) stay on the first row and the secondary buttons go on their own row, because one row was wider than a 1366 px screen.
- Known remaining: the Wallets page needs ~1017 px of content width; at a 1024 px window it still scrolls/clips slightly.

## D-026 — Dashboard and POS rebuilt to the new layouts
- **Dashboard:** greeting + date + "new invoice" button, KPI cards with a tinted icon chip and a green/red trend line, 7-day chart with today highlighted (stacked bar series; earlier days soft blue). Data and permissions logic unchanged.
- **POS:** the cashier now sees a catalogue (category chips + responsive grid of product cards, live-filtered by the scan box) next to one invoice card (customer, cart, quick actions, totals, pay). Clicking a card does exactly what scanning does (`_add_found`: phones still ask which unit). Out-of-stock accessories are disabled; cards are keyboard-focusable.
- Under 1060 px of page width the catalogue and the cart are shown one at a time (a "Products" toggle), because both do not fit; adding a product returns to the cart. The "#" column of the cart is hidden.
- New Lucide icon `trending-up` (ISC) added to `assets/icons`.
